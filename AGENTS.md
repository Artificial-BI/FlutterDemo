# AGENTS.md — Правила работы с проектом

## Основной принцип

Работай узко. Не сканируй и не анализируй весь проект, если задача явно этого не требует.

## Использование контекста

Начинай только с файлов, напрямую связанных с текущей задачей.

Расширяй контекст только если:
- файл импортируется уже открытым кодом;
- это нужно, чтобы понять текущий flow;
- это нужно для сборки, проверки типов или точечных тестов;
- задача меняет архитектуру, общую логику, публичный flow или задокументированные паттерны;
- пользователь явно просит изучить документацию или более широкий проект.

Для локальных задач не выполняй глобальный аудит.

## Перед редактированием

Сделай только короткий точечный анализ затронутой области.

Определи:
- файлы, которые нужно изменить;
- существующие компоненты, helpers, hooks, utils, widgets, mixins, animation/layout/responsive-паттерны, которые можно переиспользовать;
- очевидный риск дублирования рядом с изменяемым кодом;
- рискованные места рядом с изменяемым кодом: state, lifecycle, performance или null-safety.

Не выполняй полный поиск дублей, архитектурный обзор или аудит антипаттернов, если пользователь не попросил или изменение не затрагивает общую архитектуру.

## Правила редактирования

Делай минимальное безопасное изменение.

Не делай:
- рефакторинг несвязанного кода;
- изменение архитектуры без необходимости;
- создание дублирующей логики;
- быстрые хаки, которые только скрывают симптом;
- изменения несвязанных файлов;
- обновление документации, если не изменились задокументированное поведение, команды, архитектура, публичный flow или общие паттерны;
- изменение визуальной идентичности, поведения продукта, UX-flow или публичного API без явного требования.

Переиспользуй ближайшую существующую логику, если она доступна.

Если правильное исправление слишком большое, сделай безопасный минимальный fix и укажи ограничение в финальном отчёте.

## Требования к качеству

Все изменения должны сохранять или улучшать:
- надёжность;
- производительность;
- поддерживаемость;
- адаптивность;
- читаемость;
- тестируемость;
- существующий UX и визуальную идентичность.

Избегай исправлений, которые проходят только текущий кейс, но оставляют хрупкую логику.

Предпочитай явное, ограниченное и предсказуемое состояние вместо открытого или неконтролируемого.

Примеры обязательных стандартов качества:
- counters, indexes, progress values, animation values и user-driven state должны иметь безопасные границы;
- nullable-результаты должны обрабатываться безопасно, без force unwrap;
- высокочастотные события вроде hover, drag, scroll, resize, typing или animation ticks не должны перестраивать большие несвязанные widget trees/components;
- завершение animation или async-операций должно опираться на реальные lifecycle/status callbacks, а не на угаданные delays;
- controllers, listeners, timers, subscriptions, browser/page contexts, files и другие ресурсы должны корректно останавливаться, dispose-иться, закрываться или очищаться;
- повторяющиеся shared values вроде colors, spacing, radii, durations, thresholds и breakpoints должны жить в shared constants/tokens, если они переиспользуются в нескольких местах;
- page-specific или component-specific значения могут оставаться локальными, если они не переиспользуются.

## Архитектура и поддерживаемость

Не создавай большие монолитные файлы или методы, если изменение естественно ложится в небольшие сфокусированные helpers/components.

Если файл или метод уже большой, не переписывай его глобально. Выноси только ту часть, которая напрямую связана с текущей задачей и снижает риск.

Предпочитай:
- явные state machines для сложных flows;
- небольшие private helpers для повторяющейся логики;
- scoped rebuilds/renders;
- существующие shared design, animation, responsive, API или utility layers;
- понятные имена для magic numbers и thresholds.

Избегай:
- дублирующихся constants;
- дублирующейся interaction logic;
- дублирующейся validation logic;
- скрытых side effects;
- хрупкой связки между UI и низкоуровневыми coordinate/state calculations.

## UI / правила взаимодействия

Для UI, animation и interactive flows:

- сохраняй текущее поведение продукта, если задача не требует изменения поведения;
- при исправлении внутренних деталей держи visual output максимально близким к текущему;
- применяй interaction feedback сразу, когда это возможно;
- избегай лагов из-за ненужных deferred updates;
- держи дорогие эффекты scoped и избегай repaint/rebuild несвязанных ancestors;
- обрабатывай edge cases: первый/последний элемент, disabled state, cancelled gesture, interrupted animation, empty state и repeated interaction.

## Тесты

Добавляй или обновляй точечные тесты, когда изменение затрагивает:
- shared logic;
- state transitions;
- user interaction;
- navigation;
- animation completion;
- edge cases;
- bug-prone behavior, о котором сообщил пользователь или reviewer.

Избегай хрупких тестов, завязанных на exact pixels, exact animation frames или косметические детали реализации, если visual/golden testing не требуется явно.

Предпочитай behavioral tests:
- действие происходит;
- состояние меняется корректно;
- лимиты соблюдаются;
- edge cases не приводят к crash;
- navigation boundaries сохраняются.

## Проверки

Запускай только релевантные проверки для затронутой области:
- build;
- type check;
- lint/static analysis;
- targeted tests.

Запускай полный test suite только если:
- изменение затрагивает shared/architecture-level code;
- может сломаться несколько flows;
- пользователь явно просит.

Если проверки падают по несвязанным причинам, сообщи об этом и не исправляй несвязанные проблемы.

## Regression / rollback

Не выполняй regression analysis, rollback analysis, version comparison или восстановление старого поведения, если пользователь явно не попросил.

## Финальный отчёт

Держи отчёт коротким.

Включай только:
- что изменилось;
- изменённые файлы;
- переиспользованную существующую логику/паттерны;
- запущенные проверки;
- оставшиеся риски или ограничения.

Не повторяй эти правила в отчёте.
